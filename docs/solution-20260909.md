작성: 2026-09-09 (Asia/Seoul)
대상: `outputs/grok-build-codex-bridge` v0.2.0 / Codex CLI 0.153.4 / Codex.app 26.901.51231 / Node v22.23.0
요약과 인계는 `docs/HANDOFF.md`. 이 문서는 조사 과정과 근거를 전부 남긴 기록이다.

## 0. 결론 요약

| | 내용 |
|---|---|
| **근본 원인 1 (확정)** | `publicBridgeError`가 **모든 네트워크 계층 실패를 제네릭 문자열로 삼킨다.** Node `fetch`는 실제 코드를 `error.cause`에 숨기는데, `isAbortLike`는 최상위 `code`만 고정 목록으로 본다. 실측한 네트워크 실패 8종이 **전부** `"Grok response failed validation or execution"`으로 붕괴한다. |
| **근본 원인 2 (확정)** | 실패가 **어디에도 기록되지 않는다.** wrapper가 stderr를 Electron에 넘겨 사라진다. 그래서 원인 1이 만든 잘못된 문구를 교정할 수단이 없었다. |
| **결함 3 (확정)** | `res.writeHead()`만 호출하고 `flushHeaders()`를 하지 않아, **상류 첫 바이트(또는 10초 keepalive)까지 HTTP 응답 헤더조차 나가지 않는다.** 실측: 실제 상류 왕복에서 헤더가 9.29초에 도착. |
| **결함 4 (확정)** | **동시성 가드가 동작하지 않는다.** `if (active)` 검사가 바디 읽기 `await` 이전에 있어, 동시 3요청이 전부 200으로 통과하고 상류 호출도 3개가 동시에 떴다(실측). 문서화된 "동시 1" 보장은 거짓이다. |
| **결함 5 (확정)** | `reasoning` 항목이 **평문 요약까지 통째로 드롭**된다. `PROVIDER_OPAQUE_TYPES`와 `GROK_INPUT_ITEM_TYPES`가 서로 모순된다. 9–12회 호출 턴에서 모델이 자기 추론을 못 이어받는다. |
| **관측 사실 (확정)** | 데스크톱 실패 5건의 사망 시각이 **15077 / 15094 / 15107 / 15069 / 15113 ms** — 편차 44ms. 네트워크 플레이크가 아니라 **고정 15000ms 타이머**. Codex도 상류도 그 주체가 아님을 5개 독립 실험으로 배제(§1). |
| **가설 (미확정)** | 그 15000ms는 **macOS `getaddrinfo` 타임아웃(resolver `timeout:5` × 3 시도 = 15초)**. 반증 가능한 예측: 다음 실패의 예외는 `TypeError: fetch failed`, `cause.code ∈ {EAI_AGAIN, ETIMEOUT, ENOTFOUND}`. Phase 0 로그 한 건으로 확정 또는 기각된다. |
| **P1(체크 질문이 안 끝남)의 성격** | 전송 버그가 아니다. **프리픽스 156k + 도구 루프 35–85회 = 턴당 1.4–1.9M 토큰**의 에이전트 행동 문제. 브리지가 아니라 정책 레이어에서 고쳐야 한다. |

**한 문장:** 브리지는 실패를 *일으키지* 않는다. 브리지는 실패를 *보이지 않게* 만든다.
그래서 15초짜리 인프라 결함이 "Grok이 Codex에 안 붙는다"로 오독됐고, 이미 건강한 전송 계층을 반복해서 재검증하게 만들었다.

## 1. 측정 사실 (재현 가능)

모든 실험 스크립트는 §9 부록에 있다. 실제 실행 결과만 적는다.

### M1. 제네릭 문자열은 마스킹 버그다 — **확정**

로컬 stub 상류로 실제 실패를 일으켜 `publicBridgeError()`를 통과시킨 결과:

```
proxy drops socket mid-SSE   TypeError "terminated"    <- SocketError[UND_ERR_SOCKET]      => 제네릭
proxy truncates chunked body TypeError "terminated"    <- HTTPParserError[HPE_INVALID_...] => 제네릭
connection refused           TypeError "fetch failed"  <- Error                            => 제네릭
socket killed pre-headers    TypeError "fetch failed"  <- SocketError[UND_ERR_SOCKET]      => 제네릭
```

합성 케이스까지 포함해 10종을 분류한 결과, **네트워크 실패 8종 전부 제네릭**, abort 2종만 정상 분류:

```
DNS temporary failure (EAI_AGAIN)     => "Grok response failed validation or execution"
DNS not found (ENOTFOUND)             => "Grok response failed validation or execution"
connect timeout (UND_ERR_CONNECT_...) => "Grok response failed validation or execution"
headers timeout (UND_ERR_HEADERS_...) => "Grok response failed validation or execution"
body timeout (UND_ERR_BODY_TIMEOUT)   => "Grok response failed validation or execution"
socket closed (UND_ERR_SOCKET)        => "Grok response failed validation or execution"
TLS failure (CERT_HAS_EXPIRED)        => "Grok response failed validation or execution"
network down (ENETDOWN)               => "Grok response failed validation or execution"
client aborted (AbortError)           => "Grok request was aborted"          ← 정상
res destroyed (ERR_STREAM_DESTROYED)  => "Grok request was aborted"          ← 정상
```

원인은 `src/bridge.mjs:42-54`. `isAbortLike`는 `error.code`를 5개 상수와만 비교하고, `cause`도 같은 5개로만 재귀한다.
**Node `fetch`는 최상위 오류에 `code`를 붙이지 않는다**(실측한 8종 전부). 항상 `TypeError`이고, 진짜 코드는 `cause`에 있다.
그래서 브리징 첫날부터 지금까지, 네트워크 실패는 단 한 번도 제대로 보고된 적이 없다.

> 2026-09-08 23:31 이후 abort/DESTROYED 매핑을 넣고도 제네릭이 남은 이유가 이것이다.
> 남은 예외는 abort가 아니라 **`cause`에 코드를 숨긴 undici 오류**였다.

### M6. 응답 헤더가 즉시 전송되지 않는다 — **확정 (새 결함)**

```
writeHead only             headers at 3.01s     ← 첫 body write까지 대기
```

`src/bridge.mjs:359`는 `res.writeHead(200, …)`만 호출한다. Node는 헤더를 첫 `write()`까지 버퍼링하므로,
Codex는 **상류 첫 바이트 또는 10초 keepalive 중 빠른 쪽까지 소켓에서 아무것도 받지 못한다.**
상태 줄조차 없다. 클라이언트 입장에서는 "연결은 됐는데 서버가 죽은 것"과 구별되지 않는다.

`codex-wrapper.mjs`는 `stdio: [..., "inherit"]`로 stderr를 Electron 프로세스에 넘긴다 → 어디에도 남지 않는다.
**23:31 실패의 실제 예외는 영구히 복구 불가능하다.** 이것이 8일간 원인 규명이 안 된 구조적 이유다.

## 2. 근본 원인

### RC-1 (확정) — 오류 분류가 구조적으로 틀렸다

`isAbortLike`는 `error.code`를 본다. `fetch`는 `error.cause.code`에 넣는다.
결과: **모든** 인프라 실패가 "validation or execution"이라는, 사실과 정반대의 문구로 보고된다.
사용자는 이것을 "Grok 연동이 깨졌다"로 읽었고, 이미 건강한 전송 계층을 반복 재검증하는 데 시간을 썼다.
이 마스킹은 브리지가 존재한 이래 계속 있었다 — 네트워크 실패가 제대로 보고된 적은 한 번도 없다.

### RC-2 (확정) — 실패가 기록되지 않는다

로그가 없으므로 RC-1이 만든 잘못된 문구를 교정할 수단이 없었다.
관측성은 여기서 "있으면 좋은 것"이 아니라 **유일한 해결 경로**다.

### RC-3 (유력 가설) — 15000ms는 macOS DNS resolver 타임아웃이다

`scutil --dns`: `timeout : 5`, nameserver 5개. `getaddrinfo` 실패는 관례적으로 **5초 × 3시도 = 15초**.

이 가설만이 측정 6건을 전부 설명한다:

| 관측 | DNS 가설의 설명 |
|---|---|
| 정확히 15.0초 고정 | resolver 타임아웃은 결정론적 상수다 |
| 제네릭 문구 | `EAI_AGAIN`은 `cause`에 있어 `isAbortLike`가 못 본다 (M1에서 실측 확인) |
| Codex·상류 모두 무관 | 실패는 브리지 프로세스의 `fetch()` 안, 소켓이 열리기도 전에 발생 |
| 턴 중반에 발생 | 도구 실행 간격 동안 undici 풀 소켓이 닫히면 **새 연결 = 새 DNS 조회**가 필요해진다 |
| 오프라인 재현 불가 | 내 재현은 전부 연속 호출이라 DNS 캐시가 뜨거웠다 |
| 실패 턴의 공통점 | `find ~`, `rg` 홈 전역, `lsof -nP -iTCP`, `ps aux`, 반복 `python3` — mDNSResponder를 압박하는 부하 |
| **15초는 응답 길이 상한이 아니다** | 운영 경로에서 15.6s·17.1s·23.4s·25.0s·31.4s, 그리고 **138.8초** 응답이 정상 완료했다(§12.4). 재현 하네스에서도 15.63s·16.52s·26.91s·30.07s가 완료했다. 즉 15.0초에 발동하는 것은 "너무 오래 걸린 응답"을 끊는 타이머가 **아니다.** 아예 **시작되지 못한 요청**의 실패 시각이다 — DNS/connect의 형태와 정확히 일치한다 |

**반증 가능한 예측:** 다음 실패의 예외는 `TypeError: fetch failed` + `cause.code ∈ {EAI_AGAIN, ETIMEOUT, ENOTFOUND}`.
Phase 0 패치를 적용하면 **다음 1회 실패로 확정 또는 기각**된다.

**경쟁 가설 (차순위):** 동시성 결함(P3-1)으로 데스크톱의 부수 요청과 메인 턴이 **같은 로그인 세션으로 동시에**
상류에 열린다. 상류가 세션당 동시성을 제한하고 초과분을 고정 시간 뒤 끊는다면 역시 상수 시각 실패가 된다.
Phase 0 진단의 `signature`가 `UND_ERR_SOCKET`로 나오고 같은 시각에 두 턴이 겹쳐 기록되면 이 가설이 산다.
두 가설 모두 Phase 0 로그 한 건으로 구분된다.

> 정직하게: 아직 가설이다. 다만 해법은 가설의 참거짓과 무관하게 유효하다 —
> Phase 0은 정체를 드러내고, Phase 1은 DNS든 소켓이든 **첫 이벤트 이전 실패를 무해하게** 만든다.

### RC-4 (확정) — P1은 전송 문제가 아니다

"Grok이 잘 붙는지 체크해줘"는 ECC 스킬·config·MEMORY 전수조사를 유발한다.
매 라운드 156k 재전송 × 35–85 도구 호출. 전송을 아무리 고쳐도 이 턴은 비싸고 느리다.
**브리지에서 고칠 문제가 아니다.** 정책 레이어(§4 Phase 2)의 몫이다.

## 3. 해법 아키텍처 — 어느 레이어가 무엇을 책임지는가

| 레이어 | 책임 | 절대 하지 않을 것 |
|---|---|---|
| **브리지 (`src/`)** | 전송 정직성. 실패를 정확히 분류·보고·기록하고, 첫 이벤트 이전 실패를 안전하게 재시도한다. | 대화 내용 판단, 도구 출력 검열, 에이전트 행동 교정 |
| **Codex 정책 (`AGENTS.md` / 스킬)** | 턴 비용. "상태 점검" 같은 질문을 도구 0–1회로 끝내고, 비밀 파일 열람을 막는다. | 전송 계층 우회 |
| **운영 (스크립트·배포)** | 무중단 배포, 회귀 캡처, 검증 게이트 | 실행 중 앱 `rm -rf`/kill |

원칙: **브리지는 내용을 보지 않는다.** 브리지가 도구 출력을 읽고 검열하기 시작하면 하네스 경계가 무너지고,
Codex가 소유한 히스토리와 브리지가 보낸 히스토리가 갈라져 디버깅이 불가능해진다.

```js
  ABORTED: "aborted", AUTH: "auth", DNS: "dns", CONNECT: "connect",
  UPSTREAM_TIMEOUT: "upstream_timeout", UPSTREAM_CLOSED: "upstream_closed",
  UPSTREAM_STATUS: "upstream_status", UPSTREAM_PROTOCOL: "upstream_protocol",
  PAYLOAD: "payload", INTERNAL: "internal",
});

  [BRIDGE_ERROR.ABORTED]: "Grok request was aborted",
  [BRIDGE_ERROR.AUTH]: "Grok login expired. Run grok login.",
  [BRIDGE_ERROR.DNS]:
    "Grok is unreachable: DNS lookup for the Grok proxy failed. Check network or DNS, then retry.",
  [BRIDGE_ERROR.CONNECT]:
    "Grok is unreachable: could not connect to the Grok proxy. Check network, then retry.",
  [BRIDGE_ERROR.UPSTREAM_TIMEOUT]: "Grok did not respond in time. Retry, or shorten the turn.",
  [BRIDGE_ERROR.UPSTREAM_CLOSED]: "Grok closed the connection before finishing. Retry.",
  [BRIDGE_ERROR.UPSTREAM_PROTOCOL]: "Grok sent a malformed response. Retry.",
  [BRIDGE_ERROR.PAYLOAD]: "Grok rejected the request payload",
  [BRIDGE_ERROR.INTERNAL]: "Grok bridge failed to process the turn",
});

const DNS_CODES = new Set(["EAI_AGAIN", "ENOTFOUND", "EAI_NODATA", "EAI_NONAME", "ETIMEOUT"]);
const CONNECT_CODES = new Set([
  "ECONNREFUSED", "EHOSTUNREACH", "ENETUNREACH", "ENETDOWN", "EACCES",
  "UND_ERR_CONNECT_TIMEOUT", "CERT_HAS_EXPIRED", "UNABLE_TO_VERIFY_LEAF_SIGNATURE",
  "DEPTH_ZERO_SELF_SIGNED_CERT", "ERR_TLS_CERT_ALTNAME_INVALID",
]);
const TIMEOUT_CODES = new Set(["UND_ERR_HEADERS_TIMEOUT", "UND_ERR_BODY_TIMEOUT", "ETIMEDOUT"]);
const CLOSED_CODES = new Set(["UND_ERR_SOCKET", "ECONNRESET", "EPIPE"]);
const ABORT_CODES = new Set([
  "ABORT_ERR", "ERR_STREAM_DESTROYED", "ERR_STREAM_WRITE_AFTER_END", "ERR_STREAM_PREMATURE_CLOSE",
]);

function* chain(error, depth = 0) {
  if (!error || typeof error !== "object" || depth > 8) return;
  yield error;
  yield* chain(error.cause, depth + 1);
}

export function classifyBridgeError(error, context = {}) {
  for (const link of chain(error)) {
    const code = typeof link.code === "string" ? link.code : "";
    if (link.name === "AbortError" || ABORT_CODES.has(code))
      // 브리지가 상류를 abort하는 경우는 클라이언트가 끊었을 때뿐이다.
      // 나중에 브리지가 자체 타임아웃으로 abort하게 되면, 소켓 상태를 추측하지 말고
      // controller.abort(reason)로 이유를 명시하고 여기 context.reason으로 받는다.
      return context.reason ?? BRIDGE_ERROR.ABORTED;
    if (DNS_CODES.has(code)) return BRIDGE_ERROR.DNS;
    if (CONNECT_CODES.has(code)) return BRIDGE_ERROR.CONNECT;
    if (TIMEOUT_CODES.has(code)) return BRIDGE_ERROR.UPSTREAM_TIMEOUT;
    if (CLOSED_CODES.has(code)) return BRIDGE_ERROR.UPSTREAM_CLOSED;
    if (code.startsWith("HPE_") || link.name === "HTTPParserError")
      return BRIDGE_ERROR.UPSTREAM_PROTOCOL;
  }
  if (/this operation was aborted/i.test(String(error?.message ?? ""))) return BRIDGE_ERROR.ABORTED;
  return BRIDGE_ERROR.INTERNAL;
}

// 이름과 코드만. 메시지는 호스트·경로·토큰 조각을 담을 수 있으므로 절대 넣지 않는다.
export function errorSignature(error) {
  const parts = [];
  for (const link of chain(error)) {
    const name = typeof link.name === "string" ? link.name : "Error";
    const code = typeof link.code === "string" ? link.code : "";
    parts.push(code ? `${name}[${code}]` : name);
  }
  return parts.join(" <- ").slice(0, 200);
}

export function bridgeErrorMessage(kind, detail) {
  const base = MESSAGES[kind] ?? MESSAGES[BRIDGE_ERROR.INTERNAL];
  return detail ? `${base} (${detail})` : base;
}
```

**롤백:** 파일 삭제 + `bridge.mjs`의 `publicBridgeError` 원복. 다른 모듈에 부작용 없음.

> **설계 함정 (실제로 밟았다):** 처음에는 "클라이언트가 살아 있는데 abort가 나면 상류 장애"라는
> 세분화를 넣었다. `res.on("close")`로 `clientGone`을 래치했는데, **실패한 write가 reject되는 시점에

> 2건이 깨졌다. 소켓 상태로 의도를 추측하면 안 된다. **abort의 이유는 abort를 건 쪽이 말해야 한다.**

```js
// src/proxy.mjs
export async function openProxyStreamWithRetry(options, attempts = 2) {
  let lastError;
  for (let attempt = 1; attempt <= attempts; attempt++) {
    try {
      return await openProxyStream(options);
    } catch (error) {
      lastError = error;
      const kind = classifyBridgeError(error, { clientGone: false });
      const retryable = kind === BRIDGE_ERROR.DNS || kind === BRIDGE_ERROR.CONNECT ||
                        kind === BRIDGE_ERROR.UPSTREAM_CLOSED;
      // 클라이언트가 이미 떠났거나, 재시도 불가 종류이거나, 마지막 시도면 포기.
      if (!retryable || options.signal?.aborted || attempt === attempts) break;
      options.onRetry?.({ attempt, kind });
    }
  }
  throw lastError;
}
```

#### P1-2. DNS 조회와 소켓을 브리지 수명 동안 고정 — RC-3의 근본 대응

RC-3이 참이면 이것이 진짜 수정이다. 거짓이어도 해롭지 않다(연결 수립이 빨라진다).

> **검증 이력:** 처음에는 `node:undici`의 `Agent`로 dispatcher를 교체하려 했으나,
> **`node:undici`는 Node 22의 내장 모듈이 아니다** (`ERR_UNKNOWN_BUILTIN_MODULE`로 실측 확인).
> `undici` 패키지를 넣으면 런타임 의존성 0 원칙과 앱 번들 구조가 깨진다.
> 아래는 **전부 Node 내장만으로** 같은 효과를 내는, 실측 검증된 방식이다.

`fetch` 대신 `node:https`를 쓰면 `Agent`를 통해 keep-alive와 **DNS 조회 자체를 우리가 통제**할 수 있다.

```js
// src/proxy.mjs
import https from "node:https";
import dns from "node:dns";
import { Readable } from "node:stream";

const DNS_TTL_MS = 300_000;
const dnsCache = new Map();

// http.Agent가 기대하는 시그니처 그대로의 캐시된 lookup.
// 이것이 15초 resolver 창(RC-3)을 구조적으로 없앤다.
function cachedLookup(hostname, options, callback) {
  const key = `${hostname}:${options?.family ?? 0}`;
  const hit = dnsCache.get(key);
  if (hit && hit.expires > Date.now()) {
    process.nextTick(() => callback(null, hit.address, hit.family));
    return;
  }
  dns.lookup(hostname, options ?? {}, (error, address, family) => {
    if (!error) dnsCache.set(key, { address, family, expires: Date.now() + DNS_TTL_MS });
    // 조회에 실패해도 유효한 캐시가 있으면 그것으로 버틴다 — resolver 일시 장애에 견디게 한다.
    else if (hit) return callback(null, hit.address, hit.family);
    callback(error, address, family);
  });
}

let agent;
export function proxyAgent() {
  agent ??= new https.Agent({
    keepAlive: true,
    keepAliveMsecs: 30_000,   // 도구 실행 간격(5–20초) 동안 소켓을 살려둔다
    maxSockets: 4,
    timeout: 120_000,
    lookup: cachedLookup,
  });
  return agent;
}
```

**실측 확인 (`proto/agent-check.mjs`):**

```
http.Agent accepts keepAlive + custom lookup: true function
socket reused across a 1.2s gap: true (dns lookups performed: 1)
Readable.toWeb gives a getReader(): true
```

마지막 줄이 중요하다 — `Readable.toWeb(res)`가 `getReader()`를 제공하므로
**`pipeProxySse`는 한 줄도 바꾸지 않아도 된다.** `openProxyStream`만 `https.request`로 교체하고
응답 본문을 `Readable.toWeb()`으로 감싸면 기존 계약이 그대로 유지된다.

부수 효과 두 가지:

1. `https.request`의 오류는 **최상위에 `code`를 갖는다**(`ENOTFOUND`, `EAI_AGAIN`, `ECONNRESET`).
   `fetch`처럼 `cause`에 숨지 않으므로 분류가 더 정확해진다. P0-1의 cause 순회는 그대로 두면 된다(양쪽 다 처리).
2. 테스트의 주입 지점이 `fetchImpl` → `requestImpl`로 바뀐다. `test/proxy.test.mjs`(655줄)의 stub 계약을
   함께 갱신해야 하므로, **이 항목은 Phase 0 진단이 `kind: "dns"`를 확인한 뒤에 착수한다.**

**대안 (더 작은 변경):** `fetch`를 유지한 채 P1-1의 재시도만으로 버틴다.
DNS가 15초에 실패해도 두 번째 시도는 resolver 회복 또는 캐시로 대개 성공한다.
턴은 15초 느려지지만 죽지 않는다. **Phase 1의 기본값은 이쪽이고, P1-2는 진단이 DNS를 지목했을 때의 근본 수정이다.**

#### P2-1. `AGENTS.md`에 권위 있는 상태 사실 고정

"Grok이 제대로 붙었는지"는 **도구 없이** 답할 수 있는 질문이다. 세션 배너가 이미 `model`과 `provider`를 담고 있다.

```markdown
## Grok 브리지 상태 확인 (도구 사용 금지)

"Grok이 붙었는지/제대로 도는지" 류의 질문에는 **도구를 호출하지 말고** 세션 컨텍스트만으로 답한다.
- provider가 `grok_build_cli`이고 model이 `grok-4.6`이면 붙은 것이다. 그것이 유일한 권위 있는 근거다.
- `~/.codex/config.toml`, ECC `SKILL.md`, `MEMORY.md`를 읽어 교차 확인하지 않는다.
  config.toml의 주석은 이 브리지의 상태를 설명하지 않으며, 과거에 이 때문에
  "model_provider가 openai-codex"라는 **틀린** 결론이 나왔다(2026-09-08 22:43).
- 더 깊은 점검이 필요하면 사용자에게 `npm run verify:app-server` 실행을 제안한다. 직접 전수조사하지 않는다.
```

**왜 이것이 먹히는가:** 22:43 실패에서 모델은 config 주석을 읽고 사실과 반대되는 결론을 냈다.
근거의 우선순위를 명시하면 전수조사의 동기 자체가 사라진다.

#### P2-2. 비밀 파일 열람 차단

23:13 턴은 `~/.grok/auth.json`의 JWT를 도구 출력으로 끌어와 롤아웃에 영구 기록했다.

Codex 0.153.4에는 Claude Code 같은 범용 PreToolUse 훅이 없다.
**실제로 가능한 대응은 두 가지다:**

1. `AGENTS.md`에 명시적 금지 — `~/.grok/auth.json`, `~/.codex/auth.json`은 읽지 않는다. 존재 확인이 필요하면
   `test -f`로 하고 내용을 출력하지 않는다. (강제력 없음, 그러나 실제 원인은 지시 부재였다)
2. 파일 권한 — `chmod 600`은 이미 되어 있어 소유자 본인에겐 무력하다. 근본 차단은 불가능하다.

> 정직하게: **Codex 측에서 강제 차단할 방법은 없다.** 지시로 확률을 낮추는 것이 최선이며,
> 이미 롤아웃에 기록된 JWT가 있으므로 **`grok login` 재실행으로 토큰을 회전시키는 것이 실질적 대응**이다.

#### P2-3. 전용 `CODEX_HOME` — 권장하되 선택

`~/.codex/config.toml`의 `model = "grok-4.6"` 핀이 일반 Codex에도 적용된다.
`launch-desktop.mjs`의 `open -n` 인자에 `--env CODEX_HOME=<절대경로>`를 추가하면 완전히 분리된다.
`CODEX_CLI_PATH`가 이미 같은 방식으로 전달되고 있으므로 경로는 검증된 것이다 —
다만 `open --env`는 `~`를 확장하지 않으므로 `path.join(homedir(), ".codex-grok")`처럼 절대경로를 만들어 넘겨야 한다.
wrapper는 `{ ...process.env }`로 자식에게 그대로 전달하므로 Codex까지 도달한다.

- **얻는 것:** config·MCP·스킬 세트를 Grok 전용으로 슬림화 가능 → M8의 156k 프리픽스를 직접 줄일 수 있다.
- **잃는 것:** 세션 히스토리·ChatGPT 로그인이 분리된다. 재로그인 필요.
- **되돌리기:** `--env` 한 줄 제거.

프리픽스 156k 중 119,669자가 `world_state`(스킬·메모리·플러그인 목록)이므로, **여기가 가장 큰 레버다.**

### Phase 3 — 전송 견고화 (선택, Phase 0–1 안정화 후)

Phase 0에서 나온 진단 데이터로 우선순위를 정한 뒤 착수한다. 지금 한꺼번에 하지 않는다.

#### P3-1. 단일 동시성 가드가 실제로 동작하지 않는다 — **실측 확정, 우선순위 상향**

`src/bridge.mjs:332`의 `if (active) return json(429, …)`는 **바디를 읽는 `await` 이전**에 있고,
`active = true`는 `src/bridge.mjs:356`에서 그 이후에 설정된다. 그 사이에 도착한 요청은 전부 검사를 통과한다.

실측 (동시 3요청, 바디를 두 청크로 전송):

```
statuses: 200,200,200
max concurrent upstream calls (single-flight should keep this at 1): 3
```

**429 경로는 사실상 죽은 코드다.** 브리지가 보장한다고 문서화한 "동시 1"은 성립하지 않는다.
데스크톱은 메인 턴 외에 부수 요청(제목 생성, 시각화 등)을 낼 수 있으므로, 같은 로그인 세션으로
Grok 스트림 여러 개가 동시에 열린다. 상류가 세션당 동시성을 제한한다면 이것이 **15초 미스터리의 후보**이기도 하다.

수정: 검사와 설정을 원자적으로.

```diff
-    if (active)
-      return json(429, { error: "Grok is busy; retry after this turn" });
     let body;
     try {
       …
       body = JSON.parse(raw);
       …
     } catch (error) { … }
+    if (active)
+      return json(429, { error: "Grok is busy; retry after this turn" });
     active = true;
```

바디를 먼저 읽고 나서 검사·설정을 **동기 구간에서 연속으로** 수행하면 경합 창이 사라진다.
(요청 바디를 버리지 않으므로 Node가 소켓을 파괴하는 문제도 없어진다.)

**증명 테스트:** 위 실측 스크립트를 그대로 `test/bridge.test.mjs`에 넣고
`maxConcurrent === 1`, `statuses`에 429가 최소 1개 포함되는지 단언한다. 패치 전에는 반드시 실패한다.

#### P3-2. `reasoning` 항목이 요약까지 통째로 버려진다 — **실측 확정**

`src/tools.mjs:35-41`의 `PROVIDER_OPAQUE_TYPES`에 `reasoning`이 들어 있어,
`toProxyInputNode`가 타입 검사 첫 줄에서 `DROP`한다. `GROK_INPUT_ITEM_TYPES`는 `reasoning`을 허용하는데
그 분기까지 도달하지 못한다 — **모순된 두 목록**이다.

실측:

```
입력: message, reasoning(요약 있음, 암호화 없음), reasoning(encrypted_content), message
살아남은 항목: message, message
보존된 reasoning 요약: 0
```

암호화된 추론을 거부하는 것은 옳다(상류가 남의 opaque blob을 못 읽는다). 그러나 **평문 요약까지 버릴 이유가 없다.**
9–12회 호출이 이어지는 턴에서 모델은 매 라운드 자기 추론의 연속성을 잃고, 그래서 같은 파일을 다시 읽는다.
이것은 P10(반복 도구 읽기)의 **전송 계층 쪽 기여분**일 수 있다.

수정 방향: `reasoning`을 opaque 목록에서 빼고, `encrypted_content` 키만 제거한 뒤
`summary`가 비어 있으면 그때 `DROP`한다. 422 위험이 있으므로 **Phase 0 진단이 켜진 상태에서** 단독으로 배포한다.

## 6. 새 성공 정의

기존 목표 문서는 "transport contract 완료"라 하고, 사용자의 체감 목표는 "데스크톱 체크 질문이 끝까지 답한다"이다.
**둘은 다른 것이며, 하나를 다른 하나로 주장할 수 없다.** 분리해서 각각 측정 가능하게 정의한다.

### 정의 A — 전송 건강 (Transport Health)

> 브리지는 Codex의 모든 `/v1/responses` 요청에 대해, **성공하거나, 정확한 이유를 말하며 실패한다.**

측정 기준 (전부 자동 검증 가능):

1. `npm test` 전건 통과, 커버리지 line/branch/function ≥ 80%
2. 오류 분류 매트릭스 A1의 10종이 **서로 다른** 사용자 메시지를 만든다. 제네릭 폴백(`internal`)에 떨어지는 케이스가 0
3. 진단 로그에 최근 20턴 기록이 존재하고, `Bearer`/JWT/홈 경로 문자열이 0건
4. B1·B2 라이브 게이트 통과
5. `npm run verify:app-server` 통과

### 정의 B — 데스크톱 턴 건강 (Desktop Turn Health)

> 데스크톱에서 던진 질문이, **턴 합계 예산 안에서 최종 답변으로 끝난다.**

측정 기준:

1. "Grok이 잘 붙는지 체크해줘" → **도구 호출 ≤ 1회**, 최종 답변 존재, 턴 합계 입력 ≤ 200k 토큰
2. 임의의 실제 작업 턴에서 턴 합계 입력이 **1M 토큰을 넘지 않는다** (현재 1.4–1.9M)
3. 최근 10턴 중 `task_complete.error`가 있는 턴이 0건
4. 진단 로그에 `turn_failed` 레코드가 0건, 또는 있다면 그 `kind`가 사용자에게 정확히 보고됐다

**핵심:** 정의 A가 100%여도 정의 B는 실패할 수 있다(RC-4). 그 반대는 성립하지 않는다.
따라서 **A는 B의 전제 조건이지 대체물이 아니다.**

- 로그가 비어 있는데 UI는 실패 → 브리지가 호출되지 않았다. Phase 1은 해당 없음이고 Codex 쪽을 봐야 한다.

그 사이에도 Phase 3(동시성·reasoning·백프레셔)은 확정된 결함 수정이므로 배포해도 진단을 오염시키지 않는다.
다만 한 번에 배포하면 "무엇이 바뀌어서 좋아졌는가"를 구분하기 어려워지므로, 위 판단 후 함께 내보내는 편이 낫다.

그리고 더 큰 문제: AGENTS.md는 이 저장소에서만 적용된다. **실제 실패는 다른 디렉터리에서 났다.**

§3의 "브리지는 내용을 보지 않는다" 원칙과 충돌하지 않는다. 이것은 대화 내용을 판단하는 것이 아니라
**전송이 자기 출처를 밝히는 것**이다. `user-agent` 헤더와 같은 범주다.

## 14. 배포 후 발견 — 단일 동시성이 서브에이전트를 죽였다 (2026-09-09 08:41)

사용자가 배포된 데스크톱에서 Codex `spawn_agent`를 시험했다. 자식 에이전트가 생성은 됐지만
추론이 **429 Too Many Requests**로 죽었다. 그 429는 상류가 아니라 **브리지가 낸 것**이다.

### 14.1 내가 만든 회귀다

P3-1 이전의 가드는 `await` 앞에 있어서 사실상 **아무것도 막지 않았다.** 그래서 부모 턴과
자식 추론이 겹쳐도 둘 다 통과했다 — 서브에이전트는 **가드가 고장나 있었기 때문에** 동작하고 있었다.
가드를 제대로 고치자 그 우연이 사라졌다.

### 14.2 단일 동시성이라는 전제 자체가 틀렸다

실제 로그인 세션으로 상류에 동시 요청을 보내 봤다:

```
3 concurrent → 3/3 OK, 전부 ~1.2초
6 concurrent → 6/6 OK, 최장 2.53초
```

상류는 동시성을 문제 삼지 않는다. 브리지의 "동시 1"은 필요보다 훨씬 엄격했고,
그 대가로 하네스의 위임 기능을 통째로 막고 있었다.

### 14.3 수정 — 유한 동시성 + 큐

`src/slots.mjs` 신규. 기본 **동시 4, 큐 8**. 넘치면 거절이 아니라 **대기**한다.

거절보다 대기가 항상 나은 이유: 브리지는 이미 응답 헤더를 보냈고 keepalive로 스트림을 살려 두며,
Codex는 400초 침묵도 견딘다(M3). 대기는 클라이언트에게 지연이지만, 429는 턴 전체를 잃는다.
큐마저 가득 찼을 때만 429를 낸다.

슬롯은 `release()`가 대기자에게 **직접 넘긴다**(카운터를 내렸다 올리지 않는다). 그래서
반납과 재획득 사이에 다른 요청이 새치기하는 경합이 없다. 큐에서 대기 중 요청이 중단되면
자리를 반납하고 `AbortError`로 끝난다.
